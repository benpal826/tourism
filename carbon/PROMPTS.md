# 단계별 구현 프롬프트 (4단계)

`PRD.md`를 기준으로 Claude Code에 단계별로 붙여 넣어 쓰는 프롬프트 모음입니다.

| 단계 | 내용 | 끝났을 때 상태 |
| --- | --- | --- |
| 1 | 기본 뼈대 작성 | 수집 → 저장 → 리포트가 끝까지 도는 최소 구조 |
| 2 | 주요 기능 추가 | PRD의 P1·P2 기능이 뼈대 위에 붙은 상태 |
| 3 | UI 디자인 | 리포트가 읽기 좋고 필터·반응형이 되는 상태 |
| 4 | PRD 충족 여부 및 버그 검토 (Playwright) | PRD 항목별 합격·불합격이 기록되고 버그가 수정된 상태 |

## 단계를 나누는 이유

- **디버깅:** 문제가 생겼을 때 "어느 단계에서 들어간 변경인가"로 원인 범위를 바로 좁힌다. 뼈대가 정상이면 2단계 이후 변경을 먼저 의심한다.
- **추후 추가:** 기능(2단계)과 화면(3단계)이 뼈대(1단계)의 모듈 경계 위에 올라가므로, 나중에 출처나 기능을 더할 때 한 곳만 건드리면 된다.
- **검증 분리:** 4단계에서 PRD 기준으로 한 번에 점검하므로, 앞 단계에서는 만드는 데만 집중하고 단계마다 최소한의 확인만 한다.

## 사용 방법

1. 프로젝트 폴더(`C:\Users\User\Desktop\탄소정책`)에서 Claude Code를 실행한다.
2. 아래 **공통 컨텍스트**를 첫 메시지에 붙이거나 `CLAUDE.md`로 저장해 둔다.
3. 단계 안의 프롬프트를 번호 순서대로 하나씩 실행한다. **완료 기준**을 통과해야 다음으로 간다.
4. 단계가 끝나면 **단계 마무리 프롬프트**를 실행하고 git 태그를 남긴다. (`stage-1`, `stage-2`, ...) 문제가 생기면 직전 태그로 되돌려 비교할 수 있다.
5. 이 폴더는 아직 git 저장소가 아니므로 먼저 `git init`을 한 뒤 시작한다.

## 공통 컨텍스트

```
이 프로젝트는 탄소 정책(배출권거래제, CBAM 등) 기사를 매일 수집·분석하는 Python 프로그램이다.
먼저 PRD.md를 읽고 전체 목표와 범위를 파악해라.

규칙:
- 이번 요청 범위를 넘는 기능은 만들지 않는다. 필요해 보이면 제안만 하고 멈춘다.
- 외부 라이브러리는 꼭 필요할 때만 추가하고 requirements.txt에 반영한다.
- 기사 본문은 저장하지 않는다. 제목, 링크, 언론사, 발행시각, 요약만 다룬다.
- 기존 DB(data/articles.db)의 데이터를 지우지 않는다. 스키마 변경은 마이그레이션으로 처리한다.
- 비밀 값(API 키, SMTP 계정)은 환경변수로만 읽고 코드·로그·DB에 남기지 않는다.
- 시각은 DB에 UTC로 저장하고, 날짜 집계와 화면 표시는 KST(config.KST)로 한다.
- 모든 설정(검색어, 키워드, 임계값)은 config.py에서만 바꾸도록 한다.
- 작업이 끝나면 바꾼 파일, 검증 방법과 결과, 남은 위험을 보고한다.
```

# 1단계 · 기본 뼈대 작성

목표: PRD의 P0(F1~F4)를 만족하는 **가장 작은 end-to-end 구조**를 만든다. 기능은 적어도 되지만, 이후 단계가 얹힐 **모듈 경계**를 이 단계에서 정확히 잡는다.

핵심 설계 원칙은 세 가지다.

- 수집, 저장, 분석, 렌더링을 서로 다른 모듈로 분리한다.
- 분석 결과는 딕셔너리(JSON 형태)로 만들고, HTML 렌더링은 그 결과만 받는다. (3단계 UI 작업이 분석 코드를 건드리지 않게 하기 위함)
- 출처는 같은 인터페이스를 가진 수집기로 추가할 수 있게 한다. (2단계 공식 출처 추가 대비)

### 1-1. 프로젝트 구조와 저장소

```
프로젝트 뼈대를 만들어라. 이미 파일이 있으면 새로 쓰지 말고, 아래 구조에 맞게 최소한으로 리팩터링해라.

폴더 구조:
  config.py              설정 (검색어, 주제·지역 키워드, 경로)
  main.py                명령 진입점: collect / report / run
  carbon/
    __init__.py
    db.py                SQLite 연결, 스키마 생성, 마이그레이션(PRAGMA user_version 사용)
    sources/
      __init__.py
      base.py            수집기 인터페이스: fetch() -> list[Article]  (Article은 dataclass)
      google_news.py     Google News RSS 수집기
    pipeline.py          수집 → 중복 제거 → 태깅 → 저장 흐름
    tagging.py           키워드 기반 주제·지역 태깅
    analysis.py          리포트용 데이터 계산 (HTML을 만들지 않고 dict만 반환)
    render.py            analysis 결과 dict -> HTML 문자열
  tests/                 pytest
  run_daily.bat
  requirements.txt

요구사항:
- articles 테이블 필드는 PRD 6장의 정의를 따른다. id는 정규화한 제목의 SHA-1.
- DB 스키마 버전은 PRAGMA user_version 으로 관리해서, 이후 단계에서 컬럼을 추가할 때 마이그레이션 함수를 하나씩 붙이면 되게 한다.
- 로깅은 logging 모듈을 쓰고 logs/app.log 와 콘솔에 함께 남긴다. print는 쓰지 않는다.

완료 기준: python main.py --help 가 동작하고, 빈 DB로 실행해도 스키마가 만들어진다.
```

### 1-2. 수집과 저장 (F1, F2)

```
수집과 저장 흐름을 구현해라.

- google_news.py: config.QUERIES 의 (언어, 검색어) 목록을 돌며 Google News RSS 를 가져온다. 최근 3일치만 요청하고, 검색어 사이에 1초 간격을 둔다.
- 한 검색어가 실패해도(네트워크, 파싱) 나머지는 계속하고, 실패한 검색어는 로그에 WARNING 으로 남긴다.
- 중복 제거: 제목에서 " - 언론사" 접미사를 떼고 소문자·공백·기호를 정규화한 값으로 id 를 만든다. 같은 id 는 최초 수집분만 남긴다.
- 발행시각은 UTC ISO8601 로 저장한다. 없으면 수집 시각을 쓴다.
- python main.py collect 가 신규 저장 건수를 검색어별로 출력한다.

완료 기준: 두 번 연속 실행했을 때 두 번째 신규 저장이 첫 번째보다 크게 줄어든다(중복 제거 동작).
```

### 1-3. 태깅과 분석 (F3, F4 데이터 부분)

```
태깅과 분석 로직을 구현해라. 이 단계에서는 HTML을 만들지 마라.

- tagging.py: config.TOPICS, config.REGIONS 의 키워드가 제목·요약에 포함되면 해당 태그를 붙인다. 영문은 소문자 비교한다.
- analysis.py 의 build_report_data(days=7) 는 아래 키를 가진 dict 를 반환한다.
    generated_at, period_days, total_articles,
    per_day: [{date, count}],
    topics: [{name, count_7d, count_1d}],
    regions: [{name, count_7d}],
    rising_terms: [{term, recent, baseline, ratio}]   # 최근 2일 vs 이전 5일
    articles: [{title, url, source, published, lang, topics, regions}]   # 최신순 60건
- 급증 키워드는 제목에서 한글 2자 이상·영문 3자 이상 단어를 추출하고 config.STOPWORDS 를 제외한다. 최근 2일에 3회 미만 등장한 단어는 제외한다.
- 이 함수는 DB만 읽고 파일을 쓰지 않는다.

완료 기준: pytest 로 임시 DB에 기사 몇 건을 넣고 build_report_data 의 키와 값 타입을 검증하는 테스트가 통과한다.
```

### 1-4. 최소 리포트와 자동 실행 (F4)

```
analysis 결과를 받아 최소한의 HTML 리포트를 만드는 render.py 와 실행 흐름을 완성해라.

- render.render_report(data) -> str : 일별 기사 수, 주제별, 지역별, 급증 키워드, 최근 기사 목록을 표 위주로 단순하게 출력한다. 디자인은 신경 쓰지 마라. (3단계에서 다룬다)
- python main.py report 는 reports/report_YYYY-MM-DD.html 을 만든다. python main.py run 은 collect 후 report 를 실행한다.
- 모든 사용자 데이터(제목, 언론사)는 HTML 이스케이프한다.
- run_daily.bat 은 프로젝트 폴더로 이동한 뒤 python main.py run 을 실행하고 오류를 logs.txt 에 남긴다.
- 작업 스케줄러 등록 명령(schtasks, 매일 08:00)을 README.md 에 적는다.

완료 기준: python main.py run 한 번으로 리포트 HTML 이 생성되고 브라우저에서 열린다.
```

### 1단계 마무리

```
1단계를 마무리해라.

1. pytest 전체를 실행하고 결과를 보고한다.
2. README.md 에 폴더 구조, 설치, 실행 명령, 각 모듈의 책임을 한 줄씩 적는다.
3. PRD.md 의 F1~F4 상태를 실제 결과에 맞게 갱신한다.
4. git add/commit 후 태그 stage-1 을 만든다. (커밋은 내가 확인한 뒤에 한다)

완료 기준(1단계 게이트): run 이 끝까지 성공하고, pytest 가 통과하며, 모듈 간 의존이 collector → db → analysis → render 한 방향으로만 흐른다.
```

# 2단계 · 주요 기능 추가

목표: 뼈대를 건드리지 않고 **기능을 모듈 단위로 얹는다.** 기능마다 새 파일과 마이그레이션 하나씩만 추가하고, 기능별로 끌 수 있게 한다. (config 플래그)

순서: 공식 출처(F7) → 정책 단계·국내 영향도(F11, F12) → 뉴스–공식 문서 연결(F16) → 출처 등급(F13) → 키워드 특이도(F14) → 기관 중요도(F15) → 무관 기사 필터(F6) → LLM 분류(F5) → 알림(F9) → 내보내기(F10). F8은 조사만 한다.
정부·공식 출처를 가장 먼저 붙이는 이유는, 단계·영향도 구분이 공식 출처 기사에서 가장 정확하게 동작하고 이후 기능의 기준선이 되기 때문이다. LLM(F5)은 규칙 기반 결과를 정교화하는 마지막 도구로 쓴다.

### 2-0. 기준선 측정

```
정확도 개선 전에 현재 상태를 측정하는 tools/baseline.py 를 새 파일로 만들어라. 기존 파일은 수정하지 마라.

- 전체 기사 수, 주제 태깅률(주제 태그가 1개 이상인 비율), 지역 태그 없는 비율을 출력한다.
- 주제 태그가 없는 기사 중 무작위 50건을 tools/sample_untagged.csv 로 저장한다.
  컬럼: id, title, source, query, 사람_판정(비워둠: 관련/무관)

완료 기준: 현재 태깅률이 출력되고 CSV 가 생성된다. 이 값을 PRD 성공 지표 표의 "현재"에 기록한다.
```

### 2-1. 정부·공식 출처 추가 (F7, 최우선)

가장 먼저 붙이는 출처다. 이후 단계·영향도 구분(F11, F12)이 공식 출처 기사에서 가장 정확하게 동작하고, 다른 기능의 기준선이 되기 때문이다.

```
정부·공식 출처 수집(F7)을 추가해라. 이 프로젝트에서 가장 우선순위가 높은 출처다.

1. 먼저 조사만 해라. 후보 출처마다 아래를 표로 보고해라.
   범위: 탄소 정책과 관련된 모든 정부 부처(환경부 포함)의 보도자료·공지·입법예고, 산하·유관기관(한국환경공단 등), 국회 입법정보(법안·입법예고), EU 집행위 기후행동 총국. 환경부는 최상위 출처로 고정한다.
   부처와 기관 목록은 내가 정해 주지 않았으니 탄소 정책과 관련된 곳을 먼저 조사해 목록으로 제안해라.
   항목: RSS 제공 여부, 수집 가능한 형식, 갱신 주기, 이용약관·robots.txt 상 자동 수집 허용 여부, 확인한 URL
   부처 명칭과 조직 개편은 추측하지 말고 실제 사이트에서 확인해라. 확인하지 못한 항목은 "미확인"으로 표시해라.
2. 허용되는 출처만 구현하고, 불명확한 곳은 구현하지 말고 나에게 물어봐라.

구현:
- sources/ 아래에 출처별 파일을 추가한다. base.Source 인터페이스를 따르고, pipeline.py 는 config.SOURCES 목록을 돌며 호출하도록 일반화한다.
- 마이그레이션으로 articles.source_type 컬럼(news / official)과 articles.agency 컬럼(발행 기관명)을 추가한다. 공식 출처 기사는 source_type='official'.
- 원문 URL을 반드시 저장한다.
- analysis.py 는 data["official"] 로 공식 발표 목록을 따로 반환한다.
- 한 출처가 실패해도 나머지는 계속 수집한다.

완료 기준: Google News 수집 결과가 변경 전후로 동일하고, 공식 출처 기사가 1건 이상 수집되어 data["official"] 에 들어 있다.
```

### 2-2. 정책 진행 단계와 국내 영향도 구분 (F11, F12)

```
공식 출처 기사에 두 가지 구분을 추가해라. 우선 규칙 기반으로 만들고, LLM 으로 정교화하는 것은 뒤 단계(F5)에서 한다.
뉴스 기사 제목으로는 이 구분을 판정하지 않는다. 뉴스는 다음 작업(F16)에서 연결된 공식 문서의 값을 따른다.

구분 1. 진행 단계 (policy_stage)
- proposed(추진): 검토, 추진, 계획, 입법예고, 의견수렴, 논의, 발표 예정 등 아직 확정되지 않은 것
- decided(확정): 공포, 고시, 시행, 개정 확정, 의결, 최종 확정 등 법적·행정적으로 확정된 것
- unknown: 판단 불가
- 판정 키워드는 config.POLICY_STAGE_RULES 에 둔다. "시행 예정"처럼 두 단계의 단어가 함께 나올 때의 우선순위 규칙(예: 예정·계획이 붙으면 proposed)을 명시해라.

구분 2. 국내 영향도 (domestic_impact)
- direct(직접 규제): 국내에 의무가 생기는 정책. 예: 배출권거래제(K-ETS), 국가 온실가스 감축목표(NDC), 국내 법령·시행령 개정
- indirect(간접): 수출·공급망 등을 거쳐 국내 기업에 영향을 주는 해외 규제. 예: EU CBAM
- reference(참고): 당장 국내 영향이 작거나 미미한 동향. 예: COP 회의 논의, 영국 CBAM 등 국내와 접점이 약한 해외 정책
- 키워드 가중치는 DB 테이블 keyword_weights(keyword, seed_weight, learned_weight, updated_at, evidence)로 관리한다.
  초기값(seed)은 config.IMPACT_SEEDS 에 둔다. 최상위는 시행 중이고 산업계 영향이 가장 큰 K-ETS(배출권거래제), CBAM, NDC 다.
  자발적 탄소시장, 탄소차액계약(CCfD, Carbon Contracts for Difference) 등은 계획 단계이거나 실질 영향이 미미할 수 있으므로 낮은 값으로 시작한다.
  탄소차액계약 키워드는 '탄소차액계약', '탄소 차액 계약', 'carbon contracts for difference', 'ccfd'를 모두 포함한다.
- python main.py reweight: 누적된 기사에서 키워드별 등장 빈도, 공식 출처에서의 등장 빈도, 확정(decided) 단계 비율을 계산해 learned_weight 를 갱신한다.
  갱신 전후 변화를 로그와 reports/weight_changes.csv 에 남겨 내가 검토할 수 있게 한다.
  seed 최상위 키워드는 learned 값이 낮아도 config.IMPACT_FLOOR 아래로 내려가지 않게 한다.
- 최종 점수는 seed 와 learned 의 혼합이다. 혼합 비율은 config 에 두고, DB에 쌓인 기간이 14일 미만이면 seed 만 쓴다.
- domestic_impact 의 direct / indirect / reference 는 최종 점수 구간으로 나눈다. 구간 경계의 애매한 사례는 임의로 정하지 말고 목록으로 보고해라.

공통:
- 마이그레이션으로 articles.policy_stage, articles.domestic_impact 컬럼을 추가한다.
- analysis.py 는 기사별 두 값을 반환하고, data["official"] 은 확정(decided)과 직접 규제(direct)가 위로 오게 정렬한다.

검증: 공식 출처 기사 30건의 판정 결과를 표로 보여줘서 내가 틀린 것을 표시할 수 있게 해라.
완료 기준: 30건 중 단계 판정 정확도 80% 이상(사람 검수 기준). 미달이면 규칙을 보강하되 범위를 넘지 마라.
```

### 2-3. 뉴스와 공식 문서 연결 (F16)

```
뉴스와 공식 문서를 연결하고 "공식 확인 여부"를 표시하는 기능(F16)을 구현해라.

배경: 뉴스 제목은 자극적으로 쓰이는 경우가 많아 사실 판단의 근거로 약하다. 그래서 정책 단계(추진/확정)와 영향도는 공식 문서에서만 판단하고, 뉴스는 화제성 신호와 공식 문서로 가는 길잡이로만 쓴다.

- 마이그레이션으로 article_links 테이블(news_id, official_id, score, method, created_at)과 articles.official_status 컬럼(confirmed / unconfirmed / n/a)을 추가한다. 공식 문서 자신은 n/a 다.
- python main.py link: 최근 N일의 뉴스 기사마다 공식 문서 후보를 찾는다. 연결 근거는 기관명·법령명·제도명(config.POLICY_ENTITY_PATTERNS)의 일치, 숫자·날짜의 일치, 제목 단어의 겹침이다. 점수가 config.LINK_MIN_SCORE 이상이면 연결한다. 기준이 낮으면 오연결이 늘므로 기본값은 높게 둔다.
- 연결된 뉴스(confirmed)는 연결된 공식 문서의 policy_stage 와 domestic_impact 를 그대로 보여준다. 뉴스 제목으로 이 값을 판정하지 않는다.
- 연결된 공식 문서가 없는 뉴스(unconfirmed)는 '공식 확인 안 됨'으로 표시한다. 단계·영향도 집계에서는 제외하고 화제성 집계에만 쓴다.
- 공식 문서가 뉴스보다 늦게 올라올 수 있으므로, unconfirmed 뉴스는 일정 시간 뒤(config.LINK_RETRY_HOURS, 기본 48시간) 한 번 더 연결을 시도한다.
- 뉴스 기사 본문은 읽지 않는다. 본문을 읽는 방안(공식 문서와 연결된 기사 등 일부에 한정)은 이번 범위에 넣지 말고, 연결 결과를 본 뒤 필요하면 제안만 해라.
- analysis.py 는 기사별 official_status 와 연결된 공식 문서 id 를 반환한다. 화제성 집계(주제별 건수, 급증 키워드)에는 모든 뉴스를 쓰고, 단계·영향도 집계에는 공식 문서만 쓴다.

검증: 최근 뉴스 50건의 연결 결과를 표로 보여줘서 내가 오연결을 표시할 수 있게 해라. 연결되지 않았지만 실제로는 대응하는 공식 문서가 있는 사례도 따로 보여라.
완료 기준: 연결된 기사 중 오연결이 10% 이하(사람 검수 기준)이고, 연결되지 않은 뉴스가 단계·영향도 집계에 들어가지 않는다.
```

### 2-4. 출처 신뢰도 등급 (F13)

```
출처 신뢰도 등급(F13)을 구현해라. 목적은 단체·업계의 주장이나 자극적으로 쓴 기사를 공식 정보와 구별해 보여주는 것이다. 매체나 단체를 평가·비난하려는 것이 아니라 "누구의 말인가"를 표시하는 것이다.

- 수집기가 RSS 항목의 source.href(언론사 주소)를 articles.source_url 로 저장하고 도메인을 추출하게 한다. 이미 저장된 기사는 도메인이 없으면 언론사명으로 판단한다.
- 등급은 관찰 가능한 기준으로 자동 부여하고 근거를 기록한다. 매체의 성향을 추측해서 단정하지 마라.
  1등급: 공식 도메인(go.kr, 국회, europa.eu, 국제기구 등)과 F7의 공식 출처
  3등급: 이름이나 도메인으로 보아 단체·협회·업계 주체인 출처 (config.ORG_NAME_PATTERNS 예: 협회, 연합, 재단, 환경운동 단체명)
  2등급: 수집 빈도가 상위이면서 위에 해당하지 않는 언론사·통신사
  0: 그 외 (빈도가 낮아 판단 불가)
- 마이그레이션으로 articles.source_tier 와 articles.source_tier_reason 컬럼(예: 'domain:go.kr', 'name-pattern:협회', 'freq-top50')을 추가한다.
- 적용은 바로 하되, 빈도 상위 50곳의 등급과 근거를 표로 보고해라. 내가 문제를 찾으면 config.SOURCE_TIER_OVERRIDES 에 넣어 보정할 수 있게 한다.
- config.SENSATIONAL_TERMS(예: 충격, 경악, 폭로, 비상)가 제목에 있으면 표시만 한다. 점수 계산이나 삭제에 쓰지 않는다.
- 규칙: 3등급 출처 기사는 리포트에서 별도 배지로 표시하고 급증 키워드와 집계의 근거로 쓰지 않는다. 같은 사안을 1·2등급 출처가 다루지 않았다면 "단일 출처 주장"으로 표시한다.

완료 기준: 빈도 상위 50곳의 등급표가 근거와 함께 보고되고, 보정 목록으로 등급을 바꿀 수 있으며, 3등급 기사가 집계에서 제외되는 것을 테스트로 확인한다.
```

### 2-5. 키워드 특이도 (F14)

```
급증 키워드를 "평소에도 많이 나오는 단어"가 아니라 "평소보다 특이하게 늘어난 단어"로 바꿔라.
현재 상위가 확대, 에너지, policy, carbon, climate, 대응 같은 일반어다. 이 도메인에서는 늘 많이 나오므로 신호가 아니다. (수학 과목 기사에 숫자가 많이 나오는 것이 특이한 일이 아닌 것과 같다.)

1. 일반어 제외: config.GENERIC_TERMS 에 carbon, energy, climate, policy, 탄소, 에너지, 정책, 확대, 대응 등 원론적인 단어를 두고 급증 후보에서 제외한다. 초기 목록은 현재 DB의 문서 빈도 상위 단어에서 뽑아 나에게 제안만 해라.
2. 상대 빈도: 단어의 최근 2일 문서 빈도를 누적(최근 30일) 평소 문서 빈도와 비교한다. 평소에도 기사의 일정 비율 이상에 나오는 단어는 후보에서 제외한다. 임계값은 config 로 분리하고 기본값은 30%로 한다.
3. 구 단위: 단어 하나보다 '탄소국경조정제도 유예'처럼 두 단어 조합(bigram)을 후보에 포함한다.
4. DB에 쌓인 기간이 14일 미만이면 평소 빈도 비교를 하지 말고 일반어 제외만 적용한다. 리포트에 그 사실을 표시한다.
5. 3등급 출처(F13 적용 후)의 기사는 집계에서 제외한다.

검증: 개선 전후 상위 15개를 나란히 보여줘라.
완료 기준: 상위 15개 중 일반어가 0개이고, 테스트 데이터에서 의도적으로 늘린 단어가 상위에 온다.
```

### 2-6. 공식 기관 중요도 산출 (F15)

```
공식 기관 중요도 산출(F15)을 구현해라. 환경부는 최상위로 고정하고, 나머지 기관은 이 프로젝트에 쌓인 데이터로 중요도를 계산한다.

완료 기준: 샘플 데이터에서 발표 수와 인용 수가 많은 기관의 점수가 높게 나오고, 환경부는 항상 1순위이며, 기관별 근거를 확인할 수 있다.
```

### 2-8. LLM 분류·요약 (F5)

### 2-9. 이메일 알림 (F9)

```
리포트 알림(F9)을 구현해라.

- carbon/notify.py: SMTP 로 HTML 리포트를 본문 또는 첨부로 발송한다. 서버·계정·비밀번호·수신자는 환경변수로만 받는다.
- python main.py run --notify 옵션이 있을 때만 발송한다. --dry-run 은 메일 내용을 콘솔에만 출력한다.
```

# 3단계 · UI 디자인

목표: **render.py 와 정적 자산만 수정**해 리포트를 읽기 좋게 만든다. analysis.py 의 데이터 구조는 바꾸지 않는다. 서버 없이 HTML 파일 하나(CSS·JS 내장)로 열려야 한다.

### 3-1. 디자인 방향과 레이아웃

```
리포트 디자인을 시작하기 전에 방향부터 정해라. 코드는 쓰지 마라.

- 사용자는 매일 아침 한 번 훑어보는 실무자다. 이를 기준으로 화면 구성안 2가지를 텍스트 와이어프레임으로 제안해라.
  (예: A. 상단 요약 + 좌측 필터 + 기사 목록 / B. 카드형 대시보드)
- 각 안의 정보 우선순위(브리핑 → 공식 발표 → 급증 키워드 → 주제·지역 분포 → 기사 목록), 장단점, 구현 난이도를 3줄로 비교해라.
- 내가 하나를 고르면 다음 프롬프트로 넘어간다.
```

### 3-2. 구현

```
선택한 안으로 render.py 를 다시 작성해라. analysis.py 와 DB 는 수정하지 마라.

- HTML 하나에 CSS·JS 를 내장하고, 외부 CDN 에 의존하지 않는다. (오프라인에서도 열려야 함)
- 상단: 날짜, 기간, 총 기사 수, 제외 건수, 오늘의 브리핑.
- 공식 발표 섹션을 기사 목록보다 위에 둔다. 항목마다 정책 단계(추진 / 확정)와 국내 영향도(직접 규제 / 간접 / 참고)를 배지로 보여주고, 확정이면서 직접 규제인 항목이 가장 눈에 띄게 한다.
- 뉴스 기사에는 공식 확인 여부(공식 확인됨 / 공식 확인 안 됨)를 표시하고, 확인된 기사는 연결된 공식 문서로 이동하는 링크를 단다.
- 출처 등급 배지(공식 / 일반 / 단체·업계 주장)를 표시한다. 3등급 기사는 시각적으로 구분하고 "단체 주장"임을 표기한다. 자극적 표현 표시(SENSATIONAL_TERMS)가 있으면 작은 표식을 단다.
- 일별 기사 수는 인라인 SVG 막대 차트, 주제·지역은 가로 막대로 그린다. 색에만 의존하지 말고 값 라벨을 함께 표시한다.
- 급증 키워드는 배율 순으로 표시하고, 클릭하면 해당 키워드가 들어간 기사만 목록에 남도록 한다.
- 기사 항목: 제목(원문 링크, 새 탭), 언론사·시각, 주제·지역 태그, 한 줄 요약, 영향도 배지(high/medium/low).
- 모든 동적 값은 이스케이프한다.

완료 기준: 샘플 데이터와 실제 데이터 모두에서 레이아웃이 깨지지 않고, 데이터가 비어 있는 섹션은 빈 칸 대신 "해당 없음"을 표시한다.
```

### 3-3. 필터와 반응형·접근성

```
리포트에 상호작용과 접근성을 더해라. 서버 없이 JavaScript 로만 구현한다.

- 접근성: 의미 있는 제목 계층(h1~h3), 필터 컨트롤에 label, 키보드만으로 모든 필터와 링크를 조작할 수 있고 포커스가 보여야 한다. 텍스트 대비 4.5:1 이상.
- 인쇄 시 필터 UI 는 숨기고 목록만 인쇄되게 한다.

완료 기준: 위 항목이 4단계 Playwright 점검에서 자동으로 검증 가능한 구조여야 한다. (필터 컨트롤에 안정적인 id 또는 data-testid 를 부여한다)
```

목표: PRD 항목을 **하나씩 검증 가능한 점검 항목으로 바꿔** 합격·불합격을 기록하고, 발견한 버그를 고친다. 새 기능은 추가하지 않는다.

### 4-1. 점검표 만들기

```
PRD.md 를 읽고 검증 계획서 docs/qa-plan.md 를 만들어라. 코드는 쓰지 마라.
```

### 4-2. Playwright 환경과 화면 테스트

```
Playwright(Python)로 리포트 화면을 자동 검증해라.

환경:
- pip install pytest-playwright 후 playwright install chromium 을 실행하고 requirements-dev.txt 에 기록한다.
- 테스트는 tests/e2e/ 에 둔다. 테스트용 고정 DB(tests/fixtures/sample.db)로 리포트를 생성해 file:// 로 연다. 실제 네트워크와 운영 DB 는 사용하지 않는다.

테스트 항목:
1. 로드: 콘솔 에러와 실패한 네트워크 요청이 0건, 제목과 브리핑이 보인다.
2. 섹션: 공식 발표, 급증 키워드, 주제·지역 분포, 기사 목록이 모두 렌더링된다. 빈 섹션은 "해당 없음"이 보인다.
3. 필터: 주제·지역·영향도·기간·검색 각각과 조합이 건수와 목록을 올바르게 바꾼다. 결과 없음 안내가 나온다. 새로고침 후에도 URL 해시로 상태가 유지된다.
4. 급증 키워드 클릭: 해당 키워드를 포함한 기사만 남는다.
5. 링크: 기사 링크가 새 탭(target=_blank)이고 rel="noopener" 를 가진다.
6. 반응형: 360px, 768px, 1280px 에서 가로 스크롤이 없고 주요 컨트롤이 보인다. 각 크기의 스크린샷을 reports/qa/ 에 저장한다.
7. 다크 모드: color_scheme="dark" 에서 본문 텍스트와 배경의 대비가 4.5:1 이상이다.
8. 접근성: Tab 키만으로 모든 필터와 첫 기사 링크에 도달하고 포커스 표시가 보인다. 이미지·컨트롤에 접근 가능한 이름이 있다. (axe-core 를 쓸 수 있으면 위반 0건을 확인)
9. 보안: 제목에 <script>alert(1)</script> 가 든 기사를 넣었을 때 스크립트가 실행되지 않고 글자 그대로 표시된다.

실패한 테스트는 고치지 말고 먼저 결과 표로 보고해라.
```
