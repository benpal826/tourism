# 탄소정책 모니터링 시스템 PRD

작성일: 2026-11-03

## 1. 배경 및 문제 정의

배출권거래제(ETS)와 탄소국경조정제도(CBAM)처럼 빠르게 바뀌는 탄소 규제를 매일 사람이 직접 검색해 추적하기엔 비용이 크고 누락이 잦습니다. 이 시스템은 관련 기사를 매일 자동 수집·분류해 정책 변화와 이슈 트렌드를 한눈에 보게 하는 것을 목표로 합니다.

- **문제 1:** 한국어·영어 매체에 정보가 흩어져 있어 하루 단위 점검에 시간이 든다.
- **문제 2:** 같은 기사가 여러 검색어로 중복 노출되어 실제 이슈의 크기를 가늠하기 어렵다.
- **문제 3:** "어떤 주제가 갑자기 늘었는지" 같은 추세는 사람이 체감으로만 판단한다.

현재 상태: 1~3단계(뼈대, 주요 기능, 화면)를 구현하고 4단계 점검을 했습니다. 점검 항목 76개 중 61개 합격(충족률 80.3%)이고, 남은 불합격은 주제 태깅률 하나입니다 (`docs/qa-report.md`).

## 2. 목표와 비목표

핵심 목표는 "매일 아침 한 페이지로 전날 탄소정책 변화를 파악한다"입니다.

**목표**

- ETS, CBAM, 탄소가격, NDC 등 핵심 주제의 국내외 기사를 매일 자동 수집한다.
- 기사를 주제·지역별로 분류하고 중복을 제거한다.
- 최근 7일 추세와 급증 키워드를 리포트로 보여준다.
- 정부·공식 출처를 1순위로 수집하고, 정책의 진행 단계(추진 / 확정)를 구분한다.
- 사실 판단(단계, 영향도)은 공식 문서에서만 하고, 뉴스는 화제성 신호로 쓴다. 뉴스는 관련 공식 문서와 연결하고, 연결되지 않으면 "공식 확인 안 됨"으로 표시한다.
- 정책을 국내 영향도(직접 규제 / 간접 / 참고)로 나눠, 당장 의무가 생기는 정책이 먼저 보이게 한다.
- 출처 신뢰도 등급을 표시해, 단체 주장이나 자극적으로 쓴 기사를 공식 정보와 구별한다.
- 급증 키워드는 일반어를 제외하고 평소보다 특이하게 늘어난 단어만 보여준다.
- 정책 변화가 있을 때 사람이 놓치지 않도록 알려준다. (다음 단계)

**비목표**

- 실시간 시세 예측이나 투자 판단 제공
- 기사 전문 재배포(저작권): 제목·출처·링크만 저장·표시
- 다수 사용자용 웹 서비스 (초기에는 개인·소규모 팀 로컬 실행)

## 3. 사용자와 주요 시나리오

주 사용자는 탄소 규제가 업무에 영향을 주는 실무자와 정책 모니터링 담당자입니다. (실제 사용자 집단은 오픈 이슈 1 참고)

| 사용자 | 시나리오 | 필요한 것 |
| --- | --- | --- |
| 정책·ESG 담당자 | 출근 후 리포트 한 장으로 전날 주요 소식 확인 | 주제·지역 필터, 원문 링크 |
| 수출 제조업 담당자 | CBAM 적용 범위·일정 변화 감지 | CBAM 주제 알림, 철강·알루미늄 등 업종 태그 |
| 리서치·분석가 | 주간 트렌드와 급증 이슈 파악 | 기간별 비교, 데이터 내보내기 |

**핵심 시나리오:** 사용자가 매일 아침 리포트를 열면, 하루 사이 새로 쌓인 기사와 급증 키워드가 주제별로 정리되어 있고, 관심 기사는 링크로 바로 열 수 있다.

## 5. 데이터 출처와 수집 정책

처음에는 Google News RSS 하나로 시작했고, 2단계(F7)에서 공식 출처를 추가했습니다. 출처는 `config.SOURCES` 에서 켜고 끕니다. 접속·robots·약관 확인 상태는 `docs/source-research.md`.

| 출처 | 방식 | 언어 | 상태 |
| --- | --- | --- | --- |
| Google News RSS (`google_news`) | 검색어 12개, 최근 3일(`when:3d`). 새 공식 문서 제목으로 후속 보도 검색(F16)도 같은 경로 | 한국어·영어 | 구현됨 |
| 기후에너지환경부 보도자료·공지·공고 (`official_boards`) | 게시판 목록 첫 페이지 수집 (robots 준수, 같은 호스트 2초 간격) | 한국어 | 구현됨 (최상위 고정) |
| 그 밖의 관련 부처: 산업통상부, 재정경제부, 외교부 (`official_boards`) | 동일 | 한국어 | 구현됨 |
| 산하·유관기관: 한국환경공단, 온실가스종합정보센터 (`official_boards`) | 동일 | 한국어 | 구현됨 |
| 부처 입법예고: 국민참여입법센터 (`official_boards`) | 동일 | 한국어 | 구현됨 |
| 국회 의원발의 법률안 (`assembly_bills`) | 열린국회정보 공개 API (인증키 없으면 샘플 모드). `likms.assembly.go.kr` 는 robots 전체 차단이라 접속 안 함 | 한국어 | 구현됨 |
| EU 집행위 보도자료 (`eu_presscorner`) | RSS 중 기후·배출권 관련 | 영어 | 구현됨 |
| 법제처 API, ICAP 등 | 미정 | — | 남음 |

**수집 정책**

- 하루 1회 실행하며 뉴스 검색어 사이에 1초, 같은 공식 사이트 요청 사이에 2초 간격을 둔다.
- 저장 항목은 제목, 링크, 언론사, 발행시각, 요약(RSS 제공분)으로 제한하고 기사 본문은 저장하지 않는다.
- 같은 제목(언론사 접미사 제외)은 하나로 보고 최초 수집분만 남긴다.
- 뉴스 제목은 자극적으로 쓰이는 경우가 많으므로 화제성(어떤 주제가 많이 언급되는가) 신호로만 쓴다. 정책 단계와 영향도는 공식 문서에서만 판단한다.
- 공식 기관의 중요도는 환경부를 최상위로 고정하고, 나머지는 이 프로젝트에 쌓인 데이터(관련 발표 수, 언론 후속 보도 수 등)로 산출한다. 외부 검색으로 영향력을 추정하는 것은 이후에 검토한다.
- 수집 실패 시 해당 검색어만 건너뛰고 경고를 출력한다. 플랫폼 이용약관과 robots 정책 준수는 새 출처를 추가할 때마다 확인한다.

## 6. 시스템 구조와 데이터 모델

```
출처(carbon/sources/) → pipeline.py(중복 제거·태깅·필터·등급·연결) → SQLite(data/articles.db)
                                                                      ↓
                                     llm.py(분류·요약·브리핑), agencies.py(기관 점수)
                                                                      ↓
 사용자 ← HTML 리포트(reports/) ← render.py ← analysis.py(리포트용 dict)
        ← 알림 메일(notify.py), CSV·검색(query.py)
```

작업 스케줄러가 `run_daily.bat`(→ `main.py run`)을 실행하면 수집부터 리포트 생성까지 이어지고, 모든 기사는 SQLite 한 곳에 쌓입니다. 설정(검색어, 키워드, 임계값, 가중치, 알림 조건)은 `config.py`에서 바꿉니다. `render.py`는 DB를 읽지 않고 `analysis.py`는 HTML을 만들지 않습니다. 모듈별 설명은 `README.md`.

**articles 테이블**

| 필드 | 설명 |
| --- | --- |
| id | 정규화한 제목의 SHA-1 (중복 제거 키) |
| title, url, source | 제목, 원문 링크, 언론사 |
| lang, query | 언어(ko/en), 수집에 쓴 검색어 |
| summary | RSS가 준 요약 (대부분 제목과 비슷) |
| published, collected | 발행 시각, 수집 시각 (UTC) |
| topics, regions | 쉼표로 구분한 태그 |

2단계 이후 마이그레이션(`db.MIGRATIONS`, 현재 v10)으로 더해진 것: 공식 문서 정보(source_type, agency, policy_stage, domestic_impact, impact_score, impact_keyword), 연결 상태(official_status), 출처 등급(source_tier, source_tier_reason, sensational), 관련성(relevant, relevance_reason), LLM 결과(llm_* 컬럼). 별도 테이블: article_links(뉴스–공식 문서 연결), keyword_weights, agencies, llm_usage, briefings, notify_log.

## 7. 비기능 요구사항

- **실행 환경:** Windows 11 로컬, Python 3.14. 실행에 필요한 외부 라이브러리는 feedparser·requests, 그리고 F5(LLM) 용 anthropic 이다 (`requirements.txt`). 테스트용(pytest, playwright 등)은 `requirements-dev.txt` 에 따로 둔다.
- **자동화:** Windows 작업 스케줄러로 매일 오전 8시에 `run_daily.bat`을 실행한다.
- **성능:** 검색어 12개 기준 수집·리포트 생성이 수 분 이내에 끝나야 한다. (첫 실행은 3분 안에 끝났다)
- **신뢰성:** 한 검색어가 실패해도 나머지는 계속 수집한다. 앱 로그는 `logs/app.log`에 남고, 예약 실행(`run_daily.bat`)의 콘솔 출력과 오류는 `logs.txt`에 덧붙는다.
- **확장성:** 검색어·주제·지역 키워드는 코드 수정 없이 `config.py`에서 바꾸도록 분리한다.
- **시간대:** DB에는 UTC로 저장하고, 리포트의 날짜 집계와 시각 표시는 KST(UTC+9)로 한다.
- **비용·보안:** 유료 API 는 F5(LLM) 하나다. API 키와 SMTP 계정은 환경변수로만 읽고 코드·로그·DB 에 남기지 않으며, LLM 은 일일 호출 상한(`LLM_DAILY_LIMIT`)을 둔다.

2. **2단계 · 주요 기능 추가 (다음 착수):** 아래 순서로 진행한다.
   1. 정부·공식 출처 전체 수집(F7)
   2. 정책 단계·국내 영향도 구분(F11, F12)
   3. 뉴스–공식 문서 연결(F16)
   4. 출처 신뢰도 등급(F13)
   5. 키워드 특이도(F14)
   6. 공식 기관 중요도(F15)
   7. 무관 기사 필터링(F6)
   8. LLM 분류·한 줄 요약(F5)

**저장소 이전 (2026-11-11):** 1~2단계 일부는 이전 Windows 환경에서 진행했고, 압축 파일로 옮겨 GitHub `benpal826/news` 에서 이어 갔다. 이때 git 이력과 `stage-1` 태그, `run_daily.bat` 은 옮겨 오지 못했다 (`run_daily.bat` 은 4단계 QA-B1 에서 다시 만듦). 이후 `stage-2`·`stage-3` 태그는 만들었지만 작업 환경에서 원격 저장소로 태그를 올리지 못해 로컬에만 있다. 1단계와의 비교는 태그 대신 `tests/test_gate.py`(기능을 끈 상태의 1단계 흐름)로 한다.

**오픈 이슈**

1. 실제 사용자는 본인 혼자인가, 팀인가? 팀이라면 리포트 공유 방식(이메일, 사내 폴더)을 정해야 한다.
2. 우선 관심 업종과 지역은 무엇인가? (태깅 키워드와 공식 출처 선정에 영향)
3. LLM API 사용을 허용하는가, 허용한다면 월 예산 상한은?
4. 과거 기사를 소급해 적재할 필요가 있는가? (RSS는 최근 3일치 중심)
5. 기관·키워드 중요도를 갱신하는 신호와 주기는? (제안: 매주 관련 발표 수, 언론 후속 보도 수, 확정 정책 비율로 재계산하고 변화 내역을 기록)
6. 중요도·등급 판정에 대한 사용자 피드백을 어떻게 받을 것인가? (제안: config의 보정 목록)
7. 뉴스 본문을 읽을 것인가? (제안: 공식 문서와 연결된 기사처럼 일부에 한정하고, F16 결과를 본 뒤 결정. 약관·저작권, 유료 기사, 링크 우회 문제 확인 필요)

**결정된 사항 (2026-11-03)**

- 정부 출처는 관련 부처 전부, 산하·유관기관(한국환경공단 등), 국회 입법정보까지 모두 포함한다. 환경부는 최상위로 고정한다.
- 환경부 외 기관의 중요도는 누적 데이터로 계산한다.
- 국내 영향도는 현재 기준(시행 중이고 영향이 큰 K-ETS·CBAM·NDC가 최상위)으로 시작하고, 키워드 가중치를 누적 데이터로 계속 갱신한다.
- 3등급 매체·단체는 수집 빈도와 출처 유형으로 먼저 판단해 적용하고, 문제가 있으면 사용자 피드백으로 보정한다.
- 역할을 나눈다: 공식 문서는 사실의 기준(단계, 영향도, 핵심어), 뉴스는 화제성 신호와 공식 문서로 가는 길잡이다. 뉴스는 제목 기반으로 시작하고, 공식 문서와 연결되지 않은 뉴스는 "공식 확인 안 됨"으로 표시한다.

**결정된 사항 (2026-11-13)**

- PRD–구현 불일치(4단계 QA D-1~D-10)는 PRD 를 구현에 맞춘다. Python 3.14 실행(D-8)은 PC 에서 확인하고, 알림 조건 추가(D-10)는 미정.
